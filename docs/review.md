Оценка основана на коде, прогонах на локальных данных (СПб, Самара, Челябинск, 2010–2024) и статьях
(Лазутов и др.; Lazutov, Leonenko, epiDAMIK 2026). Пункты упорядочены по влиянию на достоверность
бюллетеня. Внутри каждого: что не так → чем подтверждено → что предлагается.

## 1. Данные

**1.1. Пропуски ПЦР и отсутствие контроля качества ряда.** В выгрузках Самары и Челябинска около
трети недель без данных ПЦР (249 и 256 недель). Исходная формула превращала их в нулевую заболеваемость
гриппом («пила» 57 → 0 → 108 → 0 в декабре 2022). Теперь пропуски интерполируются и помечаются, но
модель всё равно обучается на сильно восстановленном ряде: на Челябинске общий HGB даёт R² = −0.81 на
проверочном годе, а наивный прогноз — около +0.5.
*Предложение:* метрика качества ряда в контексте (доля импутированных недель в обучении, проверке и
последних 8 неделях); порог, при котором бюллетень явно предупреждает или не строит количественный
прогноз; skill против наивного и сезонно-наивного прогноза в `model_quality` основной модели (для
возрастных групп уже сделано: `mae_skill_vs_persistence`).

**1.2. Праздничные артефакты регистрации.** Первая неделя года систематически занижена: оценка случаев
гриппа на 1-й неделе относительно среднего 52-й и 2-й недель — медиана 0.35 в СПб (в 9 из 11 сезонов
< 0.5), 0.61 в Челябинске, 0.87 в Самаре (2011–2023). Пример — СПб 2018/19, 0–14 лет: 141 → 55 → 120 на
10 тыс. Модель видит их как динамику эпидемии, а модель
БР не может их описать (занижает R²).
*Предложение:* календарный признак «новогодние недели» для HGB, исключение или сниженный вес этих
недель в невязке модели БР, упоминание в бюллетене, если текущая неделя праздничная.

**1.3. Пересмотры данных и воспроизводимость.** Данные бюллетеня пересматриваются (это отмечено в
статье), но ряд не версионируется: перезапуск на ту же дату может дать другой отчёт.
*Предложение:* сохранять снимок входного ряда (хэш + файл) в каждом запуске, в контексте —
`data_snapshot_id`; отдельный режим «как было известно на дату X» для бэктеста.

**1.4. Допущения возрастного разложения.** Доля гриппа среди ОРВИ считается одинаковой во всех
возрастах; лабораторных данных по возрастам нет.
*Предложение:* если в источнике появятся ПЦР по возрастам — использовать их; до этого — отражать
допущение в тексте (сделано в `assumption_note`).

**1.5. Доступ к данным.** Токен API зашит в код двух репозиториев; погода — только через Open-Meteo;
без сети раньше не работал даже режим `--no-weather` (исправлено).
*Предложение:* токен — в переменную окружения или секрет; кэш ответов API и погоды на диске.

## 2. Модели

**2.1. Оценка качества ML — один holdout.** `run_forecast` проверяет модель на последних 52 неделях
одним разбиением. В статье модели переобучались еженедельно 52 раза, и метрики относятся к этой
процедуре; в продукте её нет. Метрики одного сезона сильно зависят от сезона (СПб: R² 0.81 на 2018/19
и 0.52 на 2023/24).
*Предложение:* `ai4epi backtest --city ... --from ... --to ...` — скользящее переобучение с сохранением
прогнозов каждой недели; метрики по фазам волны (рост / пик / спад / межсезонье).

**2.2. Правило согласия моделей не проверено.** Пороги (±10 % для направления, 50 % для масштаба)
выбраны экспертно, направление считается по изменению от текущей недели к h = 4, поэтому немонотонная
траектория классифицируется как «стабилизация». Главный вопрос схемы статьи — растёт ли ошибка при
расхождении моделей — пока не проверен.
*Предложение:* на бэктесте (2.1) сравнить ошибку ML при «agree» и «disagree»; подобрать пороги;
учитывать форму траектории (`classify_forecast_shape` уже есть для ML).

**2.3. Механистическая модель: правдоподобие, сэмплер, параметры.**
- Ядро ABC с ε = 1 на 10 тыс. соответствует гауссовой ошибке σ = 1. При пиках 40–100 это слишком узко:
  пучок траекторий почти не показывает неопределённость (диапазон пика 36.5–38.5 при фактическом 55).
- DEMetropolisZ, 4 × 500, часто не сходится (R-hat 1.2–1.9; у возрастной модели 2.7–3.3).
- α упирается в верхнюю границу; κ, начальное число инфицированных и профиль `g` фиксированы.
- Одна волна: вторичный подъём ведёт к «post_wave» при растущих наблюдениях.

*Предложение:* правдоподобие с оцениваемым масштабом ошибки (отрицательно-биномиальное по числу
случаев или логнормальное по показателю); модель как `pytensor.scan`, чтобы использовать NUTS вместо
безградиентного сэмплера; параметризация через `alpha·beta` и `beta`; информативные априорные
распределения по прошлым сезонам города; оценка начального числа инфицированных; детектор вторичного
подъёма (рост наблюдений при фазе «спад» или «post_wave» — повод перекалибровать от новой точки).

**2.4. Возрастная механистическая модель** — шесть параметров по двум рядам, матрица контактов не
идентифицируется. *Предложение:* фиксировать структуру B (например, пропорциональное смешивание или
внешняя матрица контактов POLYMOD/Prem для России с одним масштабным множителем) — это оставит 3
параметра и сделает оценки устойчивыми.

**2.5. ML-модель.** HGB без погоды для городов без доступа к Open-Meteo; нет признаков праздников (1.2)
и пересмотров. Возрастные модели обучаются независимо, без согласования суммы групп с общим прогнозом.
*Предложение:* иерархическое согласование (reconciliation) прогнозов групп и общего ряда; проверить
CatBoost (в статье он лучше для РФ).

## 3. Отчёт и LLM-слой

**3.1. Предупреждения анализа не доходят до текста.** R-hat, импутированные недели, «ML не лучше
наивного» — в `analysis_run.json` и частично в контексте, но секции «Качество модели» их не получают.
*Предложение:* общий блок контекста `data_and_model_caveats`, обязательный для секции ограничений.

**3.2. Нет регрессионных тестов генерации.** Исходный репозиторий не содержал тестов; LLM-слой
проверяется только вручную на Ollama, а оценщики — LLM-as-a-judge.
*Предложение:* 10–20 «золотых» контекстов (разные фазы, города, согласие и расхождение) +
детерминированные проверки чисел и запрещённых утверждений в CI; периодический прогон на реальных
моделях с сохранением оценок.

**3.3. Добавление секции требует правок в 5–6 местах.** Идентификаторы секций зашиты в
`runtime_checks`, `evaluation`, `editor`, `rendering`, `figures` (при добавлении двух секций пришлось
править все эти модули).
*Предложение:* регистрировать всё через `SectionConfig.metadata` (уже частично поддерживается:
`expected_numbers`, `editor_field_roles`) — профиль редактирования, предикаты оценщика, рендер, рисунки.

## 4. Инженерия

**4.1. Производительность.** Одна модель HGB: `learning_rate = 0.001`, `max_iter = 8000`; на каждый
горизонт обучаются модели оценки, конформной калибровки и итоговая — 12 моделей по 8000 итераций.
`early_stopping=True` при `validation_fraction=None` фактически не останавливает обучение (в проверке на данных СПб — все 8000
итераций для каждого горизонта). Бэктест на 5 сезонах: вариант `learning_rate = 0.03`, 300 итераций
обучается в ~20 раз быстрее при той же точности (R² 0.802 / 0.438 / 0.620 против 0.812 / 0.425 / 0.624
в СПб).
Анализ одной недели — 45 с, с возрастными этапами — 2 мин 20 с; скользящий бэктест на 52 недели
займёт часы. *Предложение:* `learning_rate` 0.02–0.05 с ранней остановкой (проверить на бэктесте, что
качество не падает), параллельное обучение горизонтов и групп, кэш модели между неделями.

**4.2. Зависимости и CI.** Зависимости не закреплены (`>=`), с pandas 3 тесты падали на устаревшем
`dt.dayofweek` (исправлено); PyMC 6 несовместим (закреплено `<6`); `ruff` находит ~120 замечаний в
исходном коде; CI нет. *Предложение:* lock-файл (uv/poetry), GitHub Actions: `pytest -m "not slow"` на
каждый push, полный набор — по расписанию.

**4.3. Документация не соответствует репозиторию.** README ссылается на каталог `runs/` с примерами,
которого нет; лицензия в README — «All rights reserved», в `pyproject.toml` — то же; репозиторий
теперь отдельный. *Предложение:* положить один пример прогона (без LLM — анализ + отчёт фиктивного
бэкенда) и уточнить лицензию с соавторами.
